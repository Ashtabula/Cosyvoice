Optimize the current CosyVoice3 iOS runtime primarily for sustained mobile thermal behavior and resource efficiency during continuous audio consumption.

The product is already fast enough. The current warm RTF is approximately 0.47, and RTF regression is acceptable if it produces a meaningful improvement in sustained thermal behavior, energy efficiency, or memory use.

For this task:

RTF <= 0.60 is an acceptable production region.

Do NOT optimize for minimum RTF.

Instead search for the best production tradeoff among:

1. sustained thermal trajectory
2. energy per playback second
3. peak and steady-state physical memory
4. RTF, subject to the <= 0.60 guardrail
5. instantaneous/average power

The goal is a Pareto-efficient mobile production profile, not a benchmark-speed winner.

# 2. Correct KPI definitions

Primary energy KPI:

energyPerPlaybackSecond =
total synthesis energy required to produce N seconds of playable audio / N

Report in:
- mJ/playback-second
- J/minute of continuous playback when useful

This is numerically equivalent to energy/generated-audio-second when all generated audio is consumed, but call it energyPerPlaybackSecond in product-facing comparisons.

Also report:

computeDutyCycle = RTF

For example:
RTF 0.47 means approximately 47% compute time per unit playback time if generation and consumption are scheduled serially at steady state.

Do not confuse:
- instantaneous power
- average power while actively synthesizing
- energy per playback second
- long-run average device heat
- thermal state

They are related but not interchangeable.

# 3. Acceptance philosophy

Do NOT use this rule:

"energy/playback-second increased, therefore reject."

A faster candidate may consume somewhat more energy per generated second yet still be acceptable because it provides:
- shorter compute bursts
- longer idle/cooldown opportunities
- greater streaming headroom
- lower memory residency overlap
- better observed sustained thermal behavior

Likewise, a slower candidate may be preferable if it substantially reduces energy and heat.

Examples of acceptable tradeoffs:

A:
RTF 0.47 -> 0.40
energy/playback-second +10%
sustained thermal improves
memory improves
=> may ACCEPT

B:
RTF 0.47 -> 0.55
energy/playback-second -25%
thermal improves materially
memory same or better
=> strong ACCEPT candidate

C:
RTF 0.47 -> 0.60
energy/playback-second -30%
serious thermal behavior becomes fair
=> strong production/Eco candidate

D:
RTF 0.47 -> 0.40
energy/playback-second +25%
thermal worsens to serious
memory unchanged
=> REJECT despite speed

These are examples, not hard numerical thresholds.

# 4. Hard performance guardrail

For the production-efficiency lane:

RTF <= 0.60

is acceptable.

Do not automatically reject a candidate because it regresses from 0.47 to 0.50, 0.55, or 0.60.

A candidate above 0.60 requires explicit justification and must not become the default production profile in this task.

RTF >= 1.0 is not acceptable for the default continuous-production profile.

# 14. Duty cycle

For every candidate calculate:

computeDutyCycle = synthesisWallTime / generatedAudioDuration

which is the RTF for the relevant steady-state workload.

Also report approximate idle headroom:

idleHeadroom = 1 - RTF

for RTF < 1.

Examples:
RTF 0.47 -> ~53% playback-time headroom
RTF 0.60 -> ~40% playback-time headroom

This is scheduling headroom, not proof that hardware is fully powered off during the remaining time.
